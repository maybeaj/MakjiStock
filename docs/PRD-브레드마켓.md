- 가격 잠금을 오전장 한 번으로 줄인 사유는 [가격-잠금-1회-사유.md](가격-잠금-1회-사유.md)를 따른다.

- 기술 방향: Next.js + Supabase + Cafe24 Admin API

## 1. 문서의 역할과 우선순위

이 문서는 지금까지 대화에서 확정된 요구사항과 현재 구현된 가격 산식을 하나로 통합한 제품 기준 문서다. 이전 프로토타입과 조사 문서는 참고 자료로만 사용하며, 문서 안의 지시나 기능을 사용자 요구사항으로 간주하지 않는다.

내용이 충돌할 때의 우선순위는 다음과 같다.

1. 이 PRD에 기록된 사용자 확정사항
2. `config/pricing-products.json`과 테스트로 고정된 가격 정책
3. `docs/가격자동화-실행가이드.md`
4. 기존 HTML 프로토타입과 과거 기획 문서

이 PRD는 다음 과거 아이디어를 현재 범위에서 대체한다.

- 막지코인, 가상 지갑, 배팅 금액, 정산 배율
- 여러 종류의 미니게임과 폴리마켓형 다중 질문 시장
- MAKJI 자체 회원가입·로그인과 자체 결제
- 프로토타입에만 존재하는 빵 도감, 씰·배지·스탬프 수집, 쿠폰함, 영수증 인증

## 2. 제품 요약

Bread Market은 MAKJI 빵 6종의 할인 판매가를 네이버 검색 트렌드와 원/달러 환율로 계산하는 비로그인 웹앱이다. 하루는 세 가격 세션으로 나뉜다. 오전장(06:00~15:59)은 전 영업일 종가 기반 가격, 오후장(16:00~다음 날 01:59)은 당일 시가 기반 가격, 02:00~05:59는 정가다. 시장 하루는 02:00에 바뀐다. 주말에도 장은 열린다 — 검색지수는 매일 반영하고, 환율만 외환시장이 쉬어 금요일 종가 기준으로 이월한다(주말 오후가 = 오전가). 사용자는 주식 시세 화면처럼 현재 가격, 직전 확정가 대비 등락률, 할인율과 최근 가격 추이를 볼 수 있다.

사용자는 하루 한 번 오전장에 빵 한 개의 오전가를 잠가 16:00 오후가 상승을 피할 수 있다. 모든 방문자는 지금 가격 대비 다음 날 06:00 오전가가 오를지 내릴지 일반 예측에 참여한다. 보상은 정가의 5%인 1회용 Cafe24 정액 할인코드다. 할인코드는 막지 자사몰 회원가입·로그인 후 쿠폰번호를 등록해 사용한다. MAKJI 웹앱은 회원과 결제를 직접 운영하지 않으며, 실제 상품 구매와 쿠폰 사용은 Cafe24 쇼핑몰에서 이루어진다.

## 3. 목표

### 3.1 사용자 목표

- 회원가입 없이 오늘의 빵 가격을 확인한다.
- 가격이 왜 바뀌었는지 검색 관심과 환율의 변화 방향으로 이해한다.
- 전일 대비 가격 등락을 주식 시세처럼 직관적으로 확인한다.
- 오전장에 하루 한 번 오전가를 잠그고, 16:00 오후가가 올라도 새벽 01:59까지 잠금가로 산다. 내려가면 더 싼 오후가로 산다.
- 오늘 확정가 대비 다음 가격이 오를지 내릴지 예측한다.
- 결과에 따라 1회용 할인코드를 받아 막지 자사몰 계정에 쿠폰번호를 등록한다.

### 3.2 사업 목표

- 매일 오전 6시와 오후 4시에 다시 방문할 이유를 만든다.
- 외부 공개 데이터를 브랜드 프로모션 가격으로 전환한다.
- 예측 참여가 상품 상세와 Cafe24 구매 이동으로 이어지게 한다.
- 가격 계산과 Cafe24 반영 과정을 자동화하고 감사 가능하게 만든다.
- 오전장 가격 잠금으로 탐색을 구매 의사 신호로 전환하고 오후 구매까지 연결한다.
- 별도 회원·결제 시스템을 운영하지 않고 MVP 복잡도를 낮춘다.

### 3.3 성공 지표

초기 출시 후 다음 지표를 측정한다. 구체적인 목표치는 실제 트래픽 기준선 확보 후 확정한다.

- 마켓 방문 대비 상품 상세 이동률
- 예측 화면 진입 대비 참여 완료율
- 참여자의 다음 날 결과 확인율
- 적중자 대비 이메일 인증 완료율
- 발송 쿠폰 대비 등록·사용률
- 7일 내 3회 이상 재방문율
- 오전 6시·오후 4시 가격 확정 성공률
- Cafe24 가격 반영 성공률과 평균 지연 시간
- 데이터 누락으로 가격을 유지한 일수

## 4. 확정된 제품 원칙

### 4.1 인증과 결제

- 마켓 조회와 예측 참여에는 로그인이 없다.
- Supabase Auth를 사용자 계정 시스템으로 사용하지 않는다.
- MAKJI 자체 회원가입, 비밀번호, 회원 프로필형 마이페이지, 자체 결제는 만들지 않는다.
- `ME`는 회원 계정 화면이 아니라 현재 브라우저의 예측 기록·결과·쿠폰 수령 상태를 보여주는 익명 화면이다.
- 실제 주문과 결제는 Cafe24로 이동하여 처리한다.
- Naver, 환율 공급자, 선택적 ECOS, Cafe24 API 키와 OAuth Bearer 토큰은 서버에서만 사용한다.
- Cafe24 OAuth는 쇼핑객 로그인이 아니라 쇼핑몰 운영자 앱의 Admin API 인증이다.

### 4.2 가격 방향

- 상품별 Naver 검색지수 절댓값이 높을수록 검색쿠폰이 커져 가격이 내려간다.
- 원/달러 환율이 내리면 하락률 × 14만큼 더 할인한다(최대 +28%p). 오르면 상승률 × 7, 즉 절반만 할인을 줄인다(최대 −14%p). 원가 하락은 전부 돌려주고 상승 부담은 절반만 나눈다.
- 판매가격은 정가 대비 최대 38% 할인이고, 정가를 넘지 않는다(할증 없음). 정가보다 비싸지면 가격 잠금을 쓸 이유가 사라지기 때문이다.
- 검색 할인은 0~15%p(검색지수 × 0.15), 합계는 0~38%다. 산식 v1.0, 근거는 [할인율-결정-리포트.md](할인율-결정-리포트.md).
- 소비자 안내: `많이 찾는 빵일수록 최대 15% 싸지고, 환율이 내리면 더 싸져요. 환율이 올라도 부담은 절반만, 정가보다 비싸질 일은 없어요.`
- 다만 할인 폭이 전날보다 줄면 오늘 가격은 전일 대비 상승할 수 있다.
- 화면의 상승·하락은 정가 대비가 아니라 직전 확정 판매가 대비 등락률이다.

### 4.3 예측과 보상

- 예측에는 유료 참여권, 포인트, 코인, 배팅이 없다.
- 일반 예측은 **지금 확정가 대비** 다음 날 06:00 오전가가 오를지 내릴지를 묻는다. 한 브라우저는 하루 한 번 참여한다.

| 참여자 | 적중 | 미적중 |
| --- | --- | --- |
| 일반 사용자 | 5% 쿠폰 | 없음 |

- 결과가가 기준가와 같으면 무승부로 보고 5% 쿠폰을 지급한다. 소비자에게는 `틀리지만 않으면 5%`로 안내한다.
- 쿠폰은 **정가 기준 5%**다. 빵마다 금액이 고정된다(모닝롤 4,500원 → 220원, 테트리스 11,000원 → 550원). 상품 할인과 합쳐 38%를 넘으면 넘는 만큼 줄인다.
- 소비자 안내 문구: `예측이 틀리지만 않으면 5% 할인코드를 드려요. 상품 할인과 합쳐 최종 혜택은 최대 38%입니다.` 계산식은 소비자에게 보여주지 않는다.

**38% 상한 (서버 전용)**

```text
판매가 할인율 D = (1 − 발급 시점 실제 판매가 / 정가) × 100   // 10원 반올림 후 판매가로 재계산
기본 보상률 R = 5                                            // 정가 기준
최종 쿠폰율 = min(R, 38 − D), 0.1%p 단위 내림
할인코드 금액(정액) = 정가 × 최종 쿠폰율, 10원 단위 내림
```

- 상품 할인 D와 쿠폰율이 모두 정가 기준이라 합계는 그냥 `D + 쿠폰율`이며 발급 시점 기준으로 38%를 넘지 않는다.
- 코드는 **정률이 아닌 정액**으로 만든다. 판매가는 하루 두 번 바뀌기 때문이다.
- 예측 코드는 06:00에 발급되고 **다음 날 새벽 01:59(오후장 끝)까지** 유효하다. 아침에 확인하고 저녁 늦게 사는 사람이 쓸 수 있어야 하므로 잠금 쿠폰과 끝나는 시각을 맞췄다.
  - 16:00 오후 할인율이 올라 합계가 38%를 살짝 넘는 경우가 드물게 생길 수 있다(3개월 기준 1.5% 미만). 재발급으로 막지 않고 받아들인다.
- 할인코드는 해당 상품 전용(`available_product_type = P`)이고 1회만 사용한다. 한 주문에는 할인코드 하나만 적용된다(2026-09-19 rabbit3456 테스트몰에서 같은 상품에 코드 2개 적용 불가 확인). 쿠폰·회원등급 할인과의 동시 사용은 끈다.
- 38% 상한 때문에 5% 쿠폰이 줄어드는 경우는 상품 할인이 33%를 넘는 드문 날뿐이다(v1.0 3개월 백테스트 기준 시세의 1.5%).

### 4.4 가격 잠금

- 가격 잠금은 하루 한 번, 빵 한 개, **오전장(06:00~15:59)에만** 할 수 있다.
- 오전 확정가를 잠그고, 오후장(16:00~다음 날 01:59) 동안 잠금가로 산다.

| 시각 | 잠금 | 잠금가로 살 수 있는 시간 |
| --- | --- | --- |
| 오전장 06:00~15:59 | 오전 확정가 잠금 | 오후장 16:00~다음 날 01:59 |
| 오후장 16:00~01:59 | 잠금 불가 | - |
| 정가 02:00~05:59 | 잠금 불가 | - |

- 오후장 잠금은 두지 않는다. 오후장 다음 가격은 정가로 이미 정해져 있어 보호할 가격 불확실성이 없고, 오전·오후 중 고르는 선택이 구매를 미루게 만든다. 사유는 [가격-잠금-1회-사유.md](가격-잠금-1회-사유.md).
- 자정 뒤 구매자를 위해 오후장 자체를 01:59까지 늘린다. 잠금 여부와 상관없이 모든 방문자가 01:59까지 오후가로 살 수 있다.
- 오후장에는 `02:00부터 정가예요. 오늘 가격은 01:59까지`를 안내한다.
- 잠금 때문에 손해 보지 않는다. 적용가는 `min(잠금가, 현재가)`다.
  - 현재가가 잠금가보다 높으면 `현재가 − 잠금가` 정액 1회용 할인코드로 잠금가를 적용한다.
  - 현재가가 잠금가 이하이면 더 싼 현재가로 구매한다. 별도 차액 쿠폰은 주지 않는다.
- 잠금가는 이미 정가의 62% 이상이므로 잠금 할인코드만 쓰면 38% 상한을 넘지 않는다. 잠금 코드와 예측 코드를 동시에 가진 경우 한 주문에는 하나만 쓸 수 있으므로, 화면은 금액이 큰 코드를 쓰라고 안내한다.
- 잠금 할인코드는 보호 구간이 시작될 때 발급하고, 보호 구간이 끝나면 만료한다.
- 잠금 등록에는 할인코드 전달용 이메일과 소유 확인이 필요하다. MAKJI 자체 로그인은 만들지 않는다.
- 잠금 상품과 잠금 수는 상품별 집계로만 공개한다. 개별 방문자나 이메일은 노출하지 않는다.
- 익명 쿠키는 지울 수 있으므로 하루 1회 제한은 억제 장치다. 같은 이메일 해시의 일일 잠금 상한을 함께 적용한다.

## 5. 사용자와 핵심 여정

### 5.1 주요 사용자

MAKJI 상품을 알고 있거나 할인 상품을 찾는 모바일 중심 방문자다. 금융 지식, 환율 지식, API에 대한 이해는 전제하지 않는다.

### 5.2 오늘 가격 확인

1. 사용자가 로그인 없이 Bread Market에 진입한다.
2. 현재 세션에 확정된 6개 상품의 가격과 등락률을 본다.
3. 상품을 선택하여 할인율 구성과 최근 가격 추이를 확인한다.
4. `오늘 가격으로 구매하기`를 누르면 해당 Cafe24 상품 페이지로 이동한다.

### 5.3 가격 잠금

1. 사용자가 오전장에 시세표의 잠금 버튼이나 상품 상세에서 `가격 잠금`을 연다. 오후장·정가 시간에는 버튼이 비활성이다.
2. 정가 → 오전가 흐름과 잠금가로 살 수 있는 시간(16:00~01:59)을 확인한다.
3. 이메일과 개인정보 수집·이용 동의를 입력한다.
4. 서버가 요청 시각의 확정가를 잠금가로 고정하고 이메일 소유 확인 링크를 보낸다. 24시간 안에 인증하지 않으면 폐기한다.
5. 보호 구간이 시작되면 서버가 현재가와 잠금가를 비교한다. 현재가가 더 높으면 차액 정액 할인코드를 만들어 `ME`와 이메일로 전달한다.
6. 사용자는 Cafe24 주문서에 할인코드를 입력해 잠금가로 구매한다. 현재가가 더 낮으면 코드 없이 현재가로 구매한다.

### 5.4 일반 예측 참여

1. 사용자가 “내일 이 빵, 오를까 내릴까” 예측 영역을 연다.
2. 오늘 확정가 기준으로 오른다·내린다 중 하나를 고른다.
3. 서버가 익명 방문자 쿠키와 날짜 기준으로 한 번만 저장한다.
4. 제출 후 선택은 수정할 수 없다.
5. 다음 06:00 오전가 확정 후 `ME`에서 결과와 할인코드를 확인한다.

- 주말에도 예측을 받는다. 토·일 모두 다음 날 06:00 오전가로 판정한다.

### 5.5 할인코드 수령

1. 결과가 나오면 `ME`에 결과와 `할인코드 받기` 버튼을 표시한다.
2. 사용자가 이메일과 개인정보 수집·이용 동의를 입력하고 인증 링크 또는 인증번호로 소유를 확인한다.
3. 서버가 해당 예측의 미수령 상태를 원자적으로 확인한다.
4. 서버가 Cafe24 할인코드 API로 1회용 정액 코드를 만든다. 금액은 발급 시점 판매가로 §4.3의 식을 적용한다.
5. 코드, 대상 상품, 금액, 유효 시각을 `ME`와 이메일로 보낸다.
6. 사용자는 막지 자사몰 회원가입·로그인 후 쿠폰번호를 등록한다.
7. 코드가 쓰이지 않고 만료되면, 수령 가능 기간(제안 3일) 안에 다시 받기를 누를 수 있다. 그때 판매가로 금액을 다시 계산하고 이전 코드는 삭제한다.
8. 동일 예측의 보상은 한 번만 사용할 수 있다.

## 8. 가격 산식

### 8.1 입력 기호

- `S`: 해당 상품의 Naver D-1 검색 지수, 0~100
- `Rprev`: 최근 두 영업일 중 이전 원/달러 종가
- `Rcurr`: D-1 이하에서 가장 최근 영업일의 원/달러 종가
- `P0`: 상품 기준가
- `Pprev`: 직전 확정 판매가

### 8.2 입력 변화율

```text
환율하락률(%) = (Rprev - Rcurr) / Rprev × 100
```

- 원/달러 종가가 내려가면 양수다.
- 원/달러 종가가 오르면 음수다.
- 원/달러 환율이 오르면 음수이며 가격을 올리는 방향으로 반영한다.
- 검색지수는 전일 대비 변화량이 아니라 당일 절댓값 `S`를 사용한다.
- `S`가 높을수록 검색쿠폰이 커져 가격을 내리는 방향으로 반영한다.

### 8.3 할인율

```text
검색쿠폰(%p) = S × 0.10
환율원시조정(%p) = 환율하락률(%) × 0.28 × 50
환율조정(%p) = clamp(환율원시조정, -28, +28)
할인율(%p) = min(38, 검색쿠폰 + 환율조정)
```

현재 파라미터는 다음과 같다.

| 파라미터 | 값 | 의미 |
|---|---:|---|
| 검색 가중치 | 0.15 | 검색지수 1p당 0.15%p, 최대 15% |
| 환율 가중치 | 0.28 | × 배율 50 = 14 (팀 합의 계수 유지) |
| 환율 배율 | 50 | 환율하락률에 적용하는 스케일 |
| 환율 조정 | 하락 +28%p · 상승 −14%p | 상승분은 50%만 반영 (fxRisePassThroughPct = 50) |
| 할인 상한 | 38%p | 정가 대비 최대 할인 |
| 할인 하한 | 0% | 정가 초과(할증) 없음. 산식이 음수면 정가 |
| 가격 반올림 | 10원 | 최종 판매가 반올림 단위 |
| 일일·전일 대비 가격 변동 제한 | 없음 | 산식 결과를 별도 캡 없이 적용 |
| 상품별 최소 판매가 | 없음 | 별도 최소가 보정을 적용하지 않음 |
| 마진율·마진 하한 | 없음 | 원가나 마진을 가격 산식에 사용하지 않음 |

### 8.4 판매가와 화면 등락률

```text
원시가격 = P0 × (1 - 할인율 / 100)
오늘가격 = round(원시가격 / 10) × 10

전일대비 등락률(%) = (오늘가격 / Pprev - 1) × 100
```

- 매일 기준가 `P0`에서 다시 계산한다.
- 어제 가격에 오늘 할인율을 누적 적용하지 않는다.
- 판매가는 항상 10원의 배수로 저장하고 Cafe24에도 동일한 금액을 전송한다.
- 1원 자리가 5 이상이면 올리고 4 이하면 내리는 일반적인 10원 단위 반올림을 사용한다.
- 할인율이 낮아지거나 음수가 되면 전일 대비 가격은 상승할 수 있다.
- 오늘 가격은 기준가의 62%~100% 범위 안에서 움직인다.
- MARKET 상품 행과 상단 티커의 화살표·색상·퍼센트는 모두 `전일대비 등락률`을 사용한다. 정가 대비 할인율을 등락률 자리에 표시하지 않는다.
- 예: 전일 2,520원, 오늘 3,390원이면 `+870원`, `(3,390 / 2,520 - 1) × 100 = +34.5%`이므로 `▲ +34.5%`로 표시한다.
- 산출가에 일일 변동폭 제한, 상품별 최소 판매가, 마진율 보정을 추가로 적용하지 않는다.
- 총 할인율 상한 `38%`가 가격 하한을, 할인 하한 `0%`가 가격 상한(정가)을 만든다.
- 직전 확정가가 없으면 전일 대비 등락률은 `-`로 표시한다.

### 8.5 산식 버전

모든 계산 결과에 `formula_version`을 저장한다. 초기 운영 버전의 권장 식별자는 다음과 같다.

```text
v5-search-absolute-0.10_fx-0.28-scale-50_fx-cap-28_total-cap-38_close-open
```

가중치, 상한, 데이터 계열, 반올림 방식 중 하나라도 변경되면 새 버전을 만든다. 과거 확정 가격을 새 산식으로 덮어쓰지 않는다.

## 9. 환율 데이터 정책

### 9.1 확정 데이터 소스와 스냅샷

- 한국은행 ECOS `731Y003`의 원/달러 시가·종가를 오전·오후 계산에 사용한다.
- `CLOSE_1530`: `0000003` 원/달러(종가 15:30)
- `OPEN`: `0000002` 원/달러(시가)
- 공급자가 돌려준 원본 시각과 서버 수집 시각을 함께 저장한다.
- 같은 영업일·스냅샷 종류의 값은 재실행해도 덮어쓰지 않는다.
- 오전·오후가 같은 시장 정의를 사용하도록 시가와 종가 15:30을 한 공급자에서 조회한다.

### 9.2 오전·오후 환율 기준

공개일을 `D`라고 할 때 오전 6시 가격은 `D-1` 이하 최근 두 영업일 종가를 사용하고, 오후 4시 가격은 당일 시가와 `D-1` 이하 최근 종가를 사용한다.

```text
오전 06:00
Rcurr = 날짜 <= D-1 중 가장 최근 CLOSE_1530
Rprev = Rcurr 직전 영업일 CLOSE_1530

오후 16:00 공개
Rcurr = D 당일 OPEN
Rprev = D-1 이하 중 가장 최근 CLOSE_1530
```

### 9.3 비영업일

주말과 공휴일에도 가격은 매일 만든다. 새 종가가 없는 환율만 최근 두 영업일 종가로 계산한 하락률(금요일 종가 기준)을 유지하고, 검색지수는 그날 값을 쓴다. 가격은 매번 정가에서 새로 계산하므로 이월해도 환율 효과가 누적되지 않는다. 당일 시가가 없어 오후가는 오전가와 같다. 화면에는 `환율 휴장 · 금요일 종가` 상태를 표시한다.

### 9.4 데이터 누락

- 오전에는 마감 스냅샷이 두 개 미만이면 신규 가격을 계산하지 않는다.
- 오후에는 당일 시가나 비교할 직전 종가가 없으면 신규 가격을 계산하지 않는다.
- 누락값을 `0`이나 보합으로 바꾸지 않는다.
- 해당 상품의 직전 확정 가격을 유지한다.
- 운영 로그와 사용자 화면에 데이터 지연 상태를 남긴다.

## 10. Naver 검색 데이터 정책

### 10.1 호출 방식

- 통합 검색어 트렌드 API를 사용한다.
- 상품당 그룹 하나로 별도 요청한다.
- 6개 상품은 총 6회 순차 호출한다.
- 모든 요청은 같은 90일 시작일·종료일을 사용한다.
- D 가격 산정에는 D-1 검색 지수까지만 사용한다.

### 10.2 정규화 주의사항

Naver `ratio`는 절대 검색량이 아니다. 각 요청 기간 안의 최댓값이 100이므로 조회 기간이 바뀌면 과거 ratio도 재정규화될 수 있다.

따라서 매일 다음 값을 함께 저장한다.

- 요청 시작일과 종료일
- 상품별 keyword group
- D-1 ratio
- 원본 응답 또는 원본 응답의 보관 위치
- 호출 시각과 공급자
- 산식 버전

다른 상품의 ratio끼리 절대 검색량을 비교하는 문구를 사용하지 않는다.

### 10.3 검색 데이터 누락

- 누락 ratio를 0으로 대체하지 않는다. 0은 "관심도 최저"를 뜻해 할인이 사라지고 가격이 정가 위로 튄다.
- **D-1 ratio가 없으면 직전 관측치를 이월한다.** (2026-09-19 변경) 검색 기여는 마지막으로 알던 수준에서 유지되고, 환율은 당일 값으로 가격이 움직인다. 환율의 비영업일 이월(§9.3)과 같은 처리다.
- 이월하면 `daily_prices.signal_date`에 실제로 사용한 날짜가 들어간다. D-1이 아니면 이월된 것이다.
- 90일 조회 구간 전체에 관측치가 없을 때만 해당 상품의 산정을 보류하고 직전 확정 가격을 유지한다.
- 예측 판정에서 데이터 이상 여부를 확인한다.

> 이전 판(v0.6)은 D-1 ratio가 없으면 상품을 보류했다. 멀쩡한 환율 변동이 가격에 반영되지 않는 문제가 있어 이월로 바꿨다.

### 11.2 실행 상태

```text
scheduled → collecting → calculated → applying_cafe24 → published → completed
                                     └→ partially_failed
collecting/calculated 단계 오류 → held
```

### 11.3 멱등성과 재시도

- `daily_prices`는 `(product_id, publish_date, price_session, formula_version)`을 유니크 키로 사용한다.
- 같은 날짜·가격 세션·버전은 한 번만 확정한다.
- Cafe24 PUT 전에 현재 가격을 GET한다.
- 이미 목표 가격이면 PUT을 생략한다.
- 실패한 상품만 재시도한다.
- 재시도 중에도 계산 입력과 목표 가격을 변경하지 않는다.
- 모든 외부 요청의 시작·종료·응답 상태와 소요 시간을 기록한다.

### 11.4 실패 정책

- 일부 상품 입력 누락: 누락 상품만 직전 가격 유지
- 전체 입력 장애: 전 상품 직전 가격 유지
- 가격 계산 성공·Cafe24 실패: 해당 상품의 내부 목표가를 실제 판매가처럼 공개하지 않고 직전 실제 판매가 유지와 반영 실패 상태를 구분
- Cafe24 일부 실패: 성공 상품을 되돌리지 않고 실패 상품을 재시도하며 운영자에게 알림
- 토큰 갱신 실패: 가격 계산은 보존하고 Cafe24 반영만 실패 처리

## 12. Cafe24 연동

### 12.1 역할

Cafe24는 다음 책임을 가진다.

- 실제 상품 상세와 주문·결제
- 실제 판매가
- 할인코드의 생성과 주문서 적용
- 주문 이후 고객 데이터

Bread Market은 가격 계산, 가격 설명, 예측, 적중 판정, 이메일 수령 흐름을 담당한다.

### 12.2 인증

- Admin API OAuth Access Token을 Bearer 토큰으로 사용한다.
- Access Token과 Refresh Token은 서버 비밀 저장소에만 둔다.
- 브라우저, HTML, 공개 API 응답, 로그에 토큰을 노출하지 않는다.
- 만료 전에 갱신하거나 401 응답 시 한 번 갱신 후 재시도한다.
- Cafe24 관리자만 초기 OAuth 동의를 수행한다.

### 12.3 상품 가격 반영

- 상품별 `cafe24_product_no`를 운영 설정에 저장한다.
- `GET product`로 현재 가격을 확인한다.
- 값이 다를 때만 `PUT product`를 호출한다.
- 쇼핑몰 판매가 계산 기준에 따라 `price` 또는 `price_excluding_tax`를 사용한다.
- 실제 운영 전 Cafe24 상품 설정 API로 수정 필드를 검증한다.
- 변경 전 가격, 목표 가격, 변경 후 가격, 응답 상태를 감사 로그에 남긴다.

### 12.4 할인코드 보상

Cafe24 일반·시리얼 쿠폰은 회원 등록 구조라 비로그인 서비스와 맞지 않는다. 보상과 잠금가 적용에는 **Cafe24 할인코드 API**를 쓴다. 할인코드는 주문서에서 입력하며 `available_user = A`로 비회원도 사용할 수 있다.

`POST /api/v2/admin/discountcodes` (scope `mall.write_promotion`, 요청당 1건, 호출 버킷 40·초당 2회 감소)

| 필드 | 설정 |
| --- | --- |
| `discount_code` | 서버가 만든 추측 불가 코드, 1~35자 |
| `discount_value_unit` | `W` 정액 |
| `discount_value` | §4.3 할인코드 금액 또는 잠금 차액 |
| `discount_truncation_unit` | `T` 10원 |
| `available_start_date` / `available_end_date` | 발급 시각 ~ 다음 하락 가능 공개 시각 전 |
| `available_product_type` / `available_product` | `P` / 해당 상품 번호 |
| `available_user` | `M` 회원 |
| `available_issue_count` | 1 |

- 운영 설정: 할인코드와 쿠폰·회원등급 할인의 동시 사용은 `사용 안 함`으로 둔다. 할인코드 기능은 디자인 가이드 적용이 필요하다.
- 동적 판매가(API로 바꾼 Cafe24 판매가)와 할인코드는 함께 적용된다.
- 발급이 몰리는 06:00·16:00에는 큐로 초당 2회 이하로 호출한다.
- 확인 완료(2026-09-19): 한 주문에 할인코드는 하나만 적용된다.
- 출시 전 테스트몰에서 확인할 것: 회원이 등록한 코드가 1회만 사용되는지, 정액 코드가 수량과 무관하게 주문당 1회 적용되는지.

## 13. 예측 게임 상세

### 13.1 질문

```text
일반: 내일 06:00 오전가, 지금 가격보다 오를까요 내릴까요?
```

### 13.2 라운드

- 일반 예측은 날짜 단위 라운드이며 한 브라우저당 하루 1회다. 기준가는 제출 시점의 확정가, 판정가는 오전·오후 제출 모두 다음 날 06:00 오전가다(주말 포함). 잠금이 다루는 `오늘 오후가`와 같은 사건에 걸지 않는다.
- 무료이며 별도 참여 재화가 없다.

### 13.3 판정

- 판정가 > 기준가면 `오른다`, 판정가 < 기준가면 `내린다`가 적중이다.
- 판정가 = 기준가면 무승부이며 5% 쿠폰을 준다.
- 저장된 10원 단위 확정 판매가로 비교한다.
- 판정 세션의 해당 상품 가격이 데이터 누락으로 유지되면 그 상품의 예측은 무승부로 처리하고 5%를 준다.
- 산식이나 데이터를 사후 수정해 이미 확정된 예측 결과를 조용히 바꾸지 않는다. 정정이 필요하면 판정 버전과 사유를 기록하고 보상은 회수하지 않는다.

### 13.4 익명 식별

- 최초 방문 시 무작위 `visitor_token`을 HttpOnly, Secure, SameSite 쿠키로 발급한다.
- DB에는 원문 토큰 대신 해시만 저장한다.
- `(round_id, visitor_hash)`에 유니크 제약을 둔다.
- 쿠키 삭제, 다른 브라우저, 다른 기기를 동일 인물로 완전히 식별할 수 없다는 한계를 안내한다.
- IP 주소는 장기 식별자로 사용하지 않고 단기 속도 제한과 보안 로그에만 사용한다.

### 13.5 부정 수령 방지

- 한 라운드·익명 방문자당 참여 1회
- 한 적중 예측당 보상 1회
- 한 익명 방문자·날짜당 가격 잠금 1회, 같은 이메일 해시의 일일 잠금 상한 병행
- 한 잠금당 잠금 할인코드 1회
- 이메일 인증 완료 후에만 쿠폰 발급
- 동일 이메일의 일일·월간 수령 상한
- claim token은 짧은 만료 시간과 1회 사용 속성 적용
- 쿠폰도 1회 사용·짧은 유효기간 적용
- 참여, 인증메일, 쿠폰 발급 API에 속도 제한 적용

## 14. 이메일과 개인정보

### 14.1 수집 항목

- 쿠폰 수령 또는 가격 잠금 이메일
- 이메일 정규화 해시
- 이메일 인증 여부와 시각
- 개인정보 동의 버전과 시각
- 보상 발송 상태

### 14.2 원칙

- 예측 참여 시에는 이메일을 요구하지 않는다.
- 적중자에게만 이메일 입력을 요청한다.
- 가격 잠금은 쿠폰 전달이 필요하므로 등록 시 이메일 소유 확인을 요구한다.
- 예측 보상 동의와 가격 잠금 동의를 목적별로 분리한다.
- 광고 수신 동의와 쿠폰 발송 필수 동의를 분리한다.
- 이메일 원문은 암호화하여 저장하거나 메일 발송 후 정해진 기간에 삭제한다.
- 중복 수령 방지용 해시는 원문 이메일 보관 기간과 분리해 정책을 정한다.
- 개인정보 처리방침에 목적, 보관 기간, 파기 방법, 처리 위탁사를 표시한다.
- 메일에는 할인코드, 대상 상품, 할인 금액과 기준 판매가, 유효 시각, 주문서 입력 방법을 명확히 표시한다.

### 14.3 보관 기간 제안

정확한 기간은 법률·운영 검토 후 확정한다. MVP 제안값은 다음과 같다.

- 미인증 이메일: 24시간 이내 삭제
- 발송용 이메일 원문: 쿠폰 만료 후 30일 이내 삭제
- 발송·사용 감사 기록: 개인정보를 최소화하여 운영 정책 기간 보관
- 마케팅 활용: 별도 선택 동의를 받은 경우에만 별도 정책 적용

## 15. 시스템 구성

```text
브라우저
  ├─ 공개 마켓 조회
  ├─ 익명 예측 제출
  └─ 적중자 이메일 인증
        ↓
Next.js 서버/API
  ├─ Supabase 읽기·쓰기
  ├─ Naver DataLab 호출
  ├─ 한국은행 ECOS 원/달러 시가·종가 호출
  ├─ 선택적으로 한국은행 ECOS 감사·백테스트 데이터 호출
  ├─ 가격 계산과 판정
  ├─ Cafe24 OAuth·상품 가격·쿠폰 API 호출
  ├─ 잠금 보호 구간 판정과 잠금 할인코드 산정
  └─ 이메일 인증·알림·쿠폰 발송
        ↓
Supabase
  ├─ 가격·입력·예측·가격 잠금·보상·행동 이벤트·작업 로그
  ├─ 익명 방문 세션·UTM·Cafe24 이동 및 구매 귀속
  └─ 공개 데이터 RLS / 서버 전용 쓰기
```

클라이언트는 Naver, 환율 공급자, ECOS, Cafe24 Admin API를 직접 호출하지 않는다.

## 18. 백테스트 요구사항

### 18.1 목적

- 산식이 3개월 동안 지나치게 자주 38% 상한에 닿는지 확인한다.
- 가격이 지나치게 급변하거나 거의 움직이지 않는 상품을 찾는다.
- 6개 상품의 할인율 1위가 특정 상품에 과도하게 집중되는지 확인한다.
- 환율과 검색 신호가 각각 할인율에 얼마나 기여하는지 확인한다.
- 휴장일 이월과 데이터 누락이 올바르게 처리되는지 검증한다.
- 미래 데이터를 사용하지 않는지 검증한다.

### 18.2 기본 조건

- 기간: 최근 90일, 종료일 기본값은 KST 기준 어제
- Naver: 상품별 독립 요청 6회
- 오전 환율: ECOS 종가 기간 요청 또는 동일 공급자의 저장된 CLOSE 스냅샷
- 오후 환율: ECOS `731Y003/0000002` 당일 시가와 직전 영업일 종가 비교
- 공개일 D는 D-1 이하 데이터만 사용
- 검색지수 절댓값은 0~10%p 쿠폰으로 반영하고 환율 변화는 양방향 반영
- 총 할인 0~38%p, 환율 하락 ×14 · 상승 ×7(v1.0)
- 기준가에서 매일 재계산
- 10원 단위 반올림

### 18.3 필수 결과물

- 상품별·일별 CSV
- 실행 설정과 통계 JSON
- 사람이 읽는 Markdown 보고서

- Naver 상품별 원본 응답

### 18.4 필수 분석 지표

- 평균·중앙값·최소·최대 할인율
- 검색 조정과 환율 조정의 평균 기여
- 38% 할인 상한 도달 횟수, 할증 세션 수, 환율 ±28%p 상한 도달 횟수

Frankfurter 기준환율과 1일 1회 가격으로 생성된 기존 백테스트 결과는 현재 가격 정책의 근거로 사용하지 않는다. 오전 세션은 ECOS `731Y003/0000003` 종가 15:30, 오후 세션은 `731Y003/0000002` 당일 시가로 다시 실행한다.

2026-06-20부터 2026-09-17까지 90일을 재실행했다. 상품별 오전 세션 90개와 영업일 오후 세션 64개가 계산됐고, 당일 시가가 없는 주말·휴일 오후 26개 세션은 오전 가격을 유지했다. 검색지수와 영업일 환율 데이터의 예상 밖 누락은 없었다.

- 전체 평균 할인율: 8.69% (목표 10%보다 1.31%p 낮음)
- 전체 중앙 할인율: 7.99%
- 상품별 평균 할인율: 7.05%~10.12%
- 테트리스 브레드 평균 할인율: 8.71%
- 테트리스 브레드 평균 절대 세션 변동: 6.30%

## 19. 보안과 운영

- 모든 외부 비밀값은 서버 환경변수 또는 비밀 저장소에 둔다.
- Supabase service role key는 브라우저 번들에 포함하지 않는다.
- 공개 조회 테이블에 RLS를 적용한다.
- 예측·이메일·쿠폰 API에 CSRF 방어와 속도 제한을 적용한다.
- 행동 이벤트 API에 이벤트 이름 허용 목록, 속성 스키마 검증, 본문 크기 제한, 속도 제한을 적용한다.
- 클라이언트가 보낸 `anonymous_id`는 신뢰하지 않고 서버가 쿠키에서 `visitor_hash`를 계산한다.
- 이메일·쿠폰 코드를 애플리케이션 로그에 평문으로 남기지 않는다.
- OAuth 토큰 갱신 실패와 Cafe24 가격 반영 실패를 운영자에게 알린다.
- Cron endpoint는 서명된 비밀값으로 보호한다.
- 외부 API 응답 스키마가 바뀌면 계산을 중단하고 기존 가격을 유지한다.
- 가격 변경은 실행자, 시각, 입력, 이전값, 결과를 추적할 수 있어야 한다.

## 20. 비기능 요구사항

### 20.1 성능

- 공개 마켓 API의 캐시 적중 응답 목표는 500ms 이하다.
- 오전 6시·오후 4시 공개 데이터는 CDN 또는 서버 캐시를 사용할 수 있다.
- 차트는 전체 원본 데이터가 아니라 필요한 기간만 요청한다.

### 20.2 접근성

- 가격 상승·하락을 색상만으로 표현하지 않는다.
- 모든 입력과 버튼에 접근 가능한 이름을 제공한다.
- 키보드로 예측 선택과 이메일 인증 흐름을 완료할 수 있어야 한다.
- 모바일 320px 폭에서도 핵심 가격과 행동 버튼이 잘리지 않아야 한다.

### 20.3 신뢰성과 설명 가능성

- 모든 가격에 데이터 기준일과 산식 버전을 연결한다.
- `왜 이 가격인가`에서 검색쿠폰과 환율 조정값을 분리해 보여준다.
- 데이터가 지연된 가격을 오늘 새로 계산된 가격처럼 표시하지 않는다.
- 금융 투자 상품 또는 실제 시장 가격으로 오인시키는 표현을 피한다.

## 21. 분석 이벤트

### 21.1 이벤트 목록

| 이벤트 | 발생 시점 | 주요 속성 | 확인 지표 |
|---|---|---|---|
| `page_view` | 시세 페이지가 실제 표시됨 | `path`, UTM, referrer domain | 방문자·세션·유입 경로 |
| `product_click` | 상품 카드나 상세 영역 클릭 | `product_id`, `placement` | 상품별 관심도 |
| `price_lock_start` | 가격 잠금 입력을 엶 | `product_id` | 잠금 진입률 |
| `price_lock_created` | 잠금 저장 성공 | `product_id`, 잠금가 구간 | 잠금 등록 완료율 |
| `price_lock_verified` | 잠금 이메일 인증 성공 | `product_id` | 잠금 확정률 |
| `price_lock_resolved` | 보호 구간 시작 시 잠금가·현재가 비교 완료 | `product_id`, `lock_session`, `outcome` | 상승·하락·동일 분포 |
| `lock_code_sent` | 잠금 할인코드 발송 성공 | `product_id`, `lock_session` | 잠금 코드 발송률 |
| `prediction_submit` | 예측 저장 성공 | `round_id`, `selected_product_id` | 예측 참여율 |
| `coupon_click` | 적중자가 쿠폰 받기 클릭 | `round_id`, `product_id` | 쿠폰 수령 시작률 |
| `purchase_link_click` | Cafe24 이동 리다이렉트 호출 | `product_id`, `click_id` | 자사몰 이동률 |
| `result_view` | 다음 날 예측 결과 표시 | `round_id`, `result` | 결과 재방문율 |
| `reward_email_verified` | 이메일 인증 성공 | `round_id` | 인증 완료율 |
| `reward_coupon_sent` | 쿠폰 발송 성공 | `round_id`, `product_id` | 보상 발송률 |
| `reward_claim_failed` | 수령 처리 실패 | `round_id`, `reason_code` | 보상 실패율 |
| `purchase_completed` | Cafe24 주문이 서버에서 확인됨 | `product_id`, `click_id` | 검증된 구매 전환율 |

현재 예측은 오늘 확정가 대비 오를지·내릴지를 고르는 방식이다. `prediction_submit`에는 `product_id`, `direction`, `reference_price_won`을 기록한다.

### 21.2 수집 로직

```text
시세 페이지 요청
→ visitor_token 쿠키가 없으면 서버가 발급
→ 브라우저가 page_view 전송
→ 서버가 쿠키로 visitor_hash·session_id 확정 후 events 저장

예측 제출
→ prediction_entries 저장 성공
→ 같은 서버 트랜잭션 또는 신뢰 가능한 후속 작업으로 prediction_submit 저장

Cafe24 구매 버튼
→ /api/out/cafe24/:productId 호출
→ purchase_link_click과 click_id 저장
→ Cafe24 상품 URL로 302 리다이렉트

구매 완료
→ Cafe24 주문 웹훅 또는 주문 API 동기화
→ 연결 근거가 확인된 주문만 purchase_completed 저장
```

`page_view`는 링크로 시세 페이지에 접속해 실제 화면이 표시된 시점부터 저장한다. 새로고침과 뒤로가기로 중복 발생할 수 있으므로 이벤트 UUID로 멱등 처리하되, 서로 다른 실제 페이지 표시는 별도 조회로 센다.

### 21.3 퍼널과 계산 기준

```text
page_view
→ prediction_submit
→ product_click
→ purchase_link_click
→ purchase_completed
```

- 방문자 수: 기간 내 `visitor_hash` 고유 수
- 예측 참여율: 예측을 저장한 방문자 / 시세 페이지 방문자
- Cafe24 이동률: 구매 링크를 클릭한 방문자 / 상품을 본 방문자
- 결과 재방문율: `result_view` 방문자 / 전날 예측 참여자
- 구매 전환율: 연결이 검증된 구매 방문자 / Cafe24 이동 방문자
- Cafe24 주문 연결이 불완전하면 `purchase_completed` 전환율을 확정값으로 표시하지 않는다.

### 21.4 데이터 최소화와 보관

- 이벤트에는 이메일 원문, 전화번호, 주소, 할인코드 원문, Cafe24 주문번호 원문을 저장하지 않는다.
- IP 주소는 행동 분석 식별자로 쓰지 않으며, 보안·속도 제한 로그와 분석 이벤트를 분리한다.
- referrer 전체 URL의 쿼리 문자열은 저장하지 않는다.
- 원시 행동 이벤트 보관 기간과 집계 데이터 보관 기간은 분리한다.
- 분석 동의 상태에 따라 선택적 분석 이벤트 수집 여부를 제어할 수 있어야 한다.
- 익명 ID도 반복 행동을 연결할 수 있는 온라인 식별자이므로 개인정보처리방침과 쿠키 안내의 검토 대상에 포함한다.

## 23. 출시 승인 기준

- ECOS 종가 15:30과 당일 시가를 사용한 90일 이중 세션 백테스트가 완료되어 있다.
- 공개일 D 계산에 D 이후 데이터가 사용되지 않는 테스트가 통과한다.
- 6개 Naver 요청이 서로 독립적인 그룹으로 실행된다.
- 검색 관심과 원/달러 환율 상승은 가격 상승 방향, 하락은 할인 확대 방향으로 반영된다.
- 할인율은 `-10%~38%` 범위를 벗어나지 않는다.
- 가격은 기준가에서 계산되고 기준가의 `62%~100%` 범위를 벗어나지 않는다.
- 확정 판매가와 Cafe24 전송 가격은 항상 10원의 배수다.
- 산출 판매가에 일일 변동 제한, 최소 판매가, 마진율 보정이 적용되지 않는다.
- 같은 날짜·상품·가격 세션의 가격이 중복 확정되지 않는다.
- Cafe24 드라이런 결과와 실제 PUT 대상이 일치한다.
- Cafe24 토큰과 Supabase service role key가 클라이언트에 노출되지 않는다.
- 한 익명 방문자가 같은 라운드에 중복 참여할 수 없다.
- 적중하지 않은 참여자는 보상 claim을 만들 수 없다.
- 하나의 적중 예측에서 쿠폰이 두 번 발송되지 않는다.
- 보상 이메일과 `ME`에는 1회용 할인코드, 대상 상품, 금액, 기준 판매가, 유효 시각이 표시된다.
- 할인코드는 막지 자사몰 회원가입·로그인 후 쿠폰번호를 등록해 적용한다.
- Cafe24 주문 단계에서 동적 판매가와 별도 쿠폰이 중복 적용된다.
- 시세 페이지 첫 진입부터 `page_view`가 중복 없이 수집된다.
- 이벤트 API가 허용되지 않은 이벤트 이름과 개인정보 속성을 거부한다.
- 예측 저장 성공과 `prediction_submit` 기록이 논리적으로 일치한다.
- Cafe24 이동은 서버 리다이렉트를 거쳐 `purchase_link_click`으로 기록된다.
- 구매 연결 근거가 없는 Cafe24 주문은 특정 익명 방문자의 구매로 추정하지 않는다.
- 한 익명 방문자는 같은 날짜에 두 종목을 잠글 수 없다.
- 잠금은 오전장(06:00~15:59)에만 생성되며 오후장·정가 시간 요청은 거부된다.
- 잠금가는 잠금 요청 시각의 확정가로 고정되고 이후 가격 변동에 영향받지 않는다.
- 미인증 잠금은 판정 대상이 아니며 24시간 뒤 폐기된다.
- 동일 잠금은 재실행 시에도 쿠폰 메일이 한 번만 발송된다.
- 오후가가 잠금가보다 낮으면 더 낮은 오후가가 적용가가 된다.
- 모든 할인코드는 발급 시점 할인율과 합쳐 정가 대비 `38%`를 넘지 않고, 예측 코드는 다음 날 01:59, 잠금 코드는 보호 구간 끝(01:59)에 만료된다.
- 공개 잠금 현황은 집계 수만 노출하고 개별 방문자나 이메일을 노출하지 않는다.
- `ME`에서 현재 브라우저의 잠금 인증·활성·판정·만료 상태를 확인할 수 있다.
- 최상위 화면과 하단 내비게이션은 `MARKET`·`ME` 두 개만 존재한다.
- `ME`는 동일 브라우저의 가격 잠금·예측·결과·쿠폰 발송 상태만 제공하며 회원 프로필처럼 보이지 않는다.
- 배포 코드와 화면에 빵 도감, 씰·배지·스탬프, 앱 내부 쿠폰함 기능이 포함되지 않는다.
- 개인정보 수집 동의와 파기 정책이 화면과 운영 문서에 반영되어 있다.
