# 가격 자동화 실행 가이드

> 2026-10-07 기준으로 고쳐 썼다. 산식 숫자는 v1.4 이고, 운영 값의 정본은 DB `pricing_versions`의 가장 최근 행이다. 산식 버전 이력은 [산식-버전.md](산식-버전.md), 할인율을 정한 근거는 [할인율 결정 리포트](할인율-결정-리포트.md)에 있다.

## 결론

소비자는 로그인하지 않아도 된다. 네이버 DataLab과 환율 API, Cafe24 Admin API 호출은 모두 Next.js 서버 또는 예약 작업에서만 실행한다. Cafe24의 Bearer 토큰은 쇼핑객 토큰이 아니라 쇼핑몰 운영자 앱의 OAuth 토큰이다.

## 현재 산식 (v1.4)

```text
검색쿠폰(%p) = 검색지수 × 0.15                     # 0~15%p
환율원시조정(%p) = 환율하락률(%) × 0.28 × 50        # = ×14
환율조정(%p) = clamp(환율원시조정, -28, +28)         # 상승분도 100% 반영
할인율(%p) = clamp(검색쿠폰 + 환율조정, 0, 25)       # 정가를 넘지 않음

원시가격 = 기준가 × (1 - 할인율 / 100)
공개가격 = round(원시가격 / 10) × 10
화면 등락률 = (현재 공개가격 / 직전 확정가격 - 1) × 100
```

공개가격은 10원 단위로 반올림한다. 같은 금액을 Supabase와 Cafe24에 저장·전송한다. 상품에 마진 하한(`products.list_margin_pct`·`min_margin_pct`)이 있으면 그 상품의 할인 상한은 `min(정책 상한, 마진 상한)`이다(`lib/pricing/daily-job.ts marginCapPct`). 지금 운영 6종은 두 값이 모두 null 이라 전부 정책 상한(25%)을 쓴다. 쿠폰과 합친 주문당 할인은 38%를 넘지 않는다(`TOTAL_CAP_PCT`).

`검색지수`는 상품별 90일 요청 안에서 0~100으로 정규화된 Naver ratio의 절댓값이다. 전일 대비 변화량은 산식에 넣지 않는다. `환율하락률`은 원/달러 환율이 내리면 양수, 오르면 음수다. 따라서 환율 하락은 할인을 늘리고 환율 상승은 할인을 줄인다.

환율 입력은 한국은행 ECOS `731Y003`의 원/달러 일별 시가(`0000002`)와 종가 15:30(`0000003`)를 한 쌍으로 사용한다. 공개일 D의 오전 6시 가격은 D-1까지 확인 가능한 최근 영업일의 시가와 종가를 비교하고, 오후 4시 가격은 그 종가와 D의 시가를 비교한다. D의 시가가 없는 주말·공휴일에는 오후 가격을 새로 계산하지 않고 오전 확정가격을 유지한다.

### 산식·쿠폰 값은 어디서 읽나

- 운영 값은 `pricing_versions`(010 마이그레이션)의 가장 최근 행이다. 어드민 `/admin/pricing`에서 고치고, 저장하면 새 버전(v1.4 → v1.5)이 추가된다. 한 번 만든 버전은 고칠 수 없다.
- 가격 크론은 매번 이 행을 읽는다(`lib/bread-market/policy-server.ts loadActivePolicy`). 못 읽거나 행이 검사(`checkPolicy`)를 통과하지 못하면 **503 으로 계산을 보류한다.** 코드의 대비값(`DEFAULT_POLICY`, v1.4)으로 가격을 내고 v1.4 로 기록하면 그날 어떤 산식이었는지 되짚을 수 없기 때문이다. 다음 크론(또는 수동 실행)에서 다시 시도한다.
- `daily_prices.formula_version`에는 그때 읽은 버전 이름이 들어간다.
- `config/pricing-products.json`은 대비값 대조(`tests/policy.test.mjs`)와 시뮬레이션 스크립트 입력용이다. 운영 크론은 이 파일을 읽지 않는다. 검색어도 운영은 `products.keywords`를 읽는다.

## 크론 일정

`vercel.json` 기준(스케줄은 UTC, 아래는 KST).

| 시각 (KST) | 경로 | 하는 일 |
|---|---|---|
| 02:00 | `/api/internal/reset-list-price` | Cafe24 가격을 정가로 복귀 |
| 02:30 | `/api/internal/sync-orders` | 최근 3일 Cafe24 주문 동기화(KPI) |
| 05:30 | `/api/internal/daily-pricing?session=am` | 오전가 계산·저장·Cafe24 반영, 전날 예측 판정 |
| 06:00·07:00·08:00·09:00·10:00 | `/api/internal/daily-pricing?session=am&onlyIfMissing=1` | 보류된 상품만 다시 계산 |
| 15:00 | `/api/internal/daily-pricing?session=pm` | 오후가 계산·저장·Cafe24 반영, 잠금 차액 코드 발급 |

Vercel Hobby 플랜이라 크론마다 하루 1회이고, 적어 둔 시각이 속한 한 시간 안 아무 때나 돈다. 그래서 몰 가격은 크론이 도는 순간 바뀐다 — 오후가는 15:00~15:59 사이에 몰에 들어간다. 앱 화면은 브라우저 시계로 06:00·16:00 정각에 바뀐다(오후가는 16:00 전에는 화면에 내려가지 않는다). 02:00 정가 복귀도 최대 02:59까지 늦을 수 있다. 분 단위로 정확해야 하면 Pro 플랜이 필요하다.

내부 라우트는 `Authorization: Bearer {CRON_SECRET}`가 없으면 401 이다.

### 수동 실행

```bash
# 계산·저장만 (Cafe24 는 건드리지 않는 드라이런)
curl -X POST -H "Authorization: Bearer $CRON_SECRET" \
  "https://<배포 주소>/api/internal/daily-pricing?session=am&date=YYYY-MM-DD"

# Cafe24 까지 반영
curl -X POST -H "Authorization: Bearer $CRON_SECRET" \
  "https://<배포 주소>/api/internal/daily-pricing?session=am&date=YYYY-MM-DD&commit=1"
```

크론(GET)은 반영(commit)이 기본이고, 수동(POST)은 `commit=1`을 붙여야 반영한다. 개발 모드에서는 `CAFE24_ALLOW_LOCAL_WRITES=1`이 없으면 Cafe24 쓰기를 보내지 않는다.

## 시뮬레이션

프로젝트 밖의 기존 환경 파일을 그대로 지정할 수 있다. 비밀값은 결과 파일에 기록하지 않는다.

```bash
npm run simulate:pricing -- \
  --env-file /Users/maybeaj/workspace/makji2/.env \
  --start 2026-06-18 \
  --end 2026-09-15 \
  --naver-provider hub \
  --fx-source ecos
```

반복 실행과 운영 환경의 `.env`에는 `BOK_ECOS_API_KEY`가 필요하다. 로컬 검증은 ECOS의 공식 `sample` 키로도 실행할 수 있지만 조회량 제한이 있어 운영용으로 사용하지 않는다. 한국수출입은행 매매기준율과 Frankfurter 기준환율은 시가·종가 쌍이 아니므로 가격 산정 입력으로 사용하지 않는다.

결과는 `artifacts/`에 JSON, CSV, Markdown으로 저장된다. 기본 설정은 `config/pricing-products.json`이다.

가중치 후보를 비교할 때도 할인·할증 범위와 평균 할인율을 함께 확인한다.

```bash
npm run simulate:pricing -- \
  --env-file /Users/maybeaj/workspace/makji2/.env \
  --start 2026-06-18 \
  --end 2026-09-15 \
  --naver-provider hub \
  --fx-source ecos \
  --search-weight 0.1 \
  --fx-weight 0.28 \
  --fx-scale 50 \
  --fx-discount-cap 28 \
  --fx-surcharge-cap 28 \
  --output artifacts/stable
```

운영에 저장된 입력(검색지수·환율 변화율)으로 산식만 바꿔 보려면 어드민 `/admin/pricing`의 90일 백테스트를 쓴다. 새로 수집하지 않고 `daily_prices`에 남은 입력으로 다시 계산한다.

## 오전 6시·오후 4시 운영 순서

1. 두 세션 모두 공개일 D-2의 네이버 검색 지수를 사용한다(`searchSignalDateOf`, `SEARCH_SIGNAL_LAG_DAYS = 2`). 오전·오후가 같은 날짜를 쓴다. 그날 값이 없으면 이전 값을 끌어오지 않고 보류한다(4번).
2. 오전 6시에는 D-1까지의 원/달러 시가·종가 중 최근 영업일 값을 골라 하락률을 계산한다.
3. 오후 4시에는 오전이 끝점으로 쓴 그 종가와 D의 원/달러 시가를 비교한다. 당일 시가가 없으면 오전 확정가격을 유지한다.
4. 검색지수가 아직 없으면 0으로 대체하지 않고 그 상품을 보류(`held`)한다. 06:00~10:00 매시 `onlyIfMissing=1` 크론이 보류된 상품만 다시 계산한다.
5. 각 세션 가격은 기준가에서 독립적으로 계산한다. 앞 세션 가격에 할인율을 재적용하지 않는다.
6. 같은 `(product_id, publish_date, price_session, formula_version)`은 한 번만 확정된다(유니크 키 + upsert).
7. 실행 이력은 `job_runs`에, Cafe24 반영 결과는 `daily_prices.cafe24_apply_status`에 남는다. 실패한 반영은 자동으로 다시 시도하지 않는다.
8. 상품에 옵션이 있으면 `config/cafe24-option-prices.ts`의 옵션 정가에 같은 할인율을 적용해 옵션 추가금도 함께 바꾼다. 몰의 옵션명이 설정과 하나라도 다르면 그 상품은 반영 전에 실패한다.

API 키와 Cafe24 토큰은 서버에만 둔다. Cafe24 토큰은 환경변수가 아니라 Supabase `cafe24_tokens`에 암호화해 둔다.

## 연결 몰: 지금은 데모몰

`CAFE24_MALL_ID`는 지금 데모몰 `rabbit3456`이다. 할인코드 발급, 몰 가격 반영, 주문 동기화(KPI)가 모두 이 몰 기준이다. 구매 버튼의 목적지는 `SHOP_TARGET`이 따로 정한다(`demo` = rabbit3456 샘플 상품, `live` = `products.shop_url`의 makji.kr 상품).

makji.kr 로 옮길 때는 두 값을 **함께** 바꿔야 한다. 하나만 바꾸면 손님은 makji.kr 로 가는데 가격·할인코드는 데모몰에 생기거나, 그 반대가 된다.

1. 배포 환경변수 `CAFE24_MALL_ID`를 makji.kr 몰 ID 로 바꾼다(멀티쇼핑몰 번호가 다르면 `CAFE24_SHOP_NO`도).
2. `SHOP_TARGET=live`로 바꾼다.
3. `/api/auth/cafe24/start`로 OAuth 를 다시 받는다. 토큰은 몰마다 한 행이라(`cafe24_tokens.mall_id`) 데모몰 토큰은 쓰이지 않는다. `node scripts/cafe24-token.mjs`로 확인한다.
4. 상품번호를 makji.kr 기준으로 바꾼다. `config/cafe24-product-map.json`은 데모몰 수동 매핑이므로 지우거나 비우고, `GET /api/internal/sync-products`(드라이런)로 이름 매칭을 확인한 뒤 `POST`로 반영한다. 어드민 상품 화면의 "연결 확인"으로 한 건씩 볼 수도 있다.
5. 어드민에서 빵마다 자사몰 주소(`shop_url`)를 채운다. 비어 있으면 구매 버튼이 makji.kr 첫 화면으로 간다.
6. makji.kr 상품의 옵션명이 `config/cafe24-option-prices.ts`와 같은지 확인한다. 다르면 가격 반영이 실패한다.
7. 재배포한 뒤 `daily-pricing`을 드라이런(POST, `commit` 없이)으로 한 번 돌려 확인하고, 다음 크론부터 반영되게 둔다.

할인코드 대신 Cafe24 쿠폰을 쓰지 않는 이유: Cafe24 쿠폰·시리얼쿠폰은 회원 전용이라 비회원·익명 구조에는 할인코드가 맞다. makji.kr 주문서 스킨에는 할인코드 입력란이 이미 있다.
