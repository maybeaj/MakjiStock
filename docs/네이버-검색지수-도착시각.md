# 네이버 검색지수 도착 시각 — 열린 결정

> 2026-10-07 기준: 가격에는 지금 D-1 이 아니라 D-2 검색지수를 쓰고(`lib/pricing/daily-job.ts` `SEARCH_SIGNAL_LAG_DAYS = 2`, 2026-09-21), 그 값이 없으면 보류한다. 오전가 따라잡기 크론은 지금 06·07·08·09·10시대(KST) 다섯 번이고(`vercel.json`), 주문 조회는 주문 동기화(`/api/internal/sync-orders`)로 하며, 잠금 카드는 서버에 발급된 차액 쿠폰이 있을 때만 쿠폰을 말한다 (현재 상태: [가격 자동화 실행 가이드](가격자동화-실행가이드.md)).

> 상태: **측정 중**. 며칠 모은 뒤 오전장 공개 시각(06:00)을 늦출지 판단한다.
> 관련: [가격 자동화 실행 가이드](가격자동화-실행가이드.md) · `vercel.json` · `app/api/internal/daily-pricing/route.ts`

## 무슨 일이 있었나

2026-09-20(일) 운영 오전가가 6종 전부 전날과 같은 값으로 나왔다. 화면 등락률은 전부 0%.

```
09-20 am  publish_date 2026-09-20  signal_date 2026-09-18   ← 기대값은 09-19
          모닝롤 4,170원 (직전 4,170, 0%)  검색 52.778
09-19 am  publish_date 2026-09-19  signal_date 2026-09-18
          모닝롤 4,170원 (직전 4,080, +2.21%)  검색 52.778
```

`signal_date` 컬럼에는 요청한 날짜가 아니라 **실제로 쓴 날짜**가 들어간다
(`route.ts` → `signal_date: search.sourceDate`). D-1 관측치가 없으면
`resolveSearchRatio`(`lib/pricing/pricing.mjs`)가 직전 관측치를 이월하기 때문이다.

크론은 **09-19T20:21Z = 09-20 05:21 KST** 에 돌았다. 그 시각 네이버 데이터랩에
09-19 치가 아직 없어서 09-18 을 이월했고, 09-19 오전가를 만들 때와 입력이
완전히 같아져(환율도 주말이라 동일) 같은 가격이 나왔다.

## 측정된 사실

문서에 갱신 시각이 명시된 것을 찾지 못해 API 를 직접 찔러 확인했다.

- 당일 데이터는 오지 않는다. **D-1 까지만** 온다.
- 없는 날짜는 0 으로 오지 않고 **배열에서 빠진다**. 그래서 이월이 발동한다.
- `endDate` 에 미래 날짜를 넣으면 `400 Invalid Date Range`.

2026-09-20 의 D-1(09-19) 도착 시각은 아래 구간까지만 좁혀졌다.

| 시각(KST) | 관측 | 출처 |
|---|---|---|
| 05:21 | 09-19 **없음** | 운영 크론이 09-18 을 이월 |
| 09:30 | 09-19 있음 | 로컬 수동 실행, signal_date=2026-09-19 |
| 09:46 | 09-19 있음 (81.25) | API 직접 조회 |

**05:21~09:30 사이**. 하루치 표본이라 확정할 수 없다.

## 지금 한 조치

1. **이월이면 가격을 만들지 않는다.** `route.ts` 가 `search.carried` 면 그 상품을
   `held` 로 두고 `daily_prices` 행을 쓰지 않는다. 이월값으로 계산하면 전날과
   같은 가격이 나오면서 화면에는 "새 가격 0%" 처럼 보이는데, 그건 거짓말이다.
   행이 없으면 화면은 마지막 확정가를 이월해 보여준다(`engine.ts realSlotAtOrBefore`).
2. **따라잡기 크론.** 보류하면 그날 오전가가 영영 안 생기므로 06·07·08·09시대(KST)에
   `onlyIfMissing=1` 로 다시 돈다. 이미 만든 상품은 건너뛴다 — 공개된 가격을
   나중 실행이 덮어쓰면 화면에 떴던 값과 달라진다. 도착 시각이 아직
   05:21~09:30 구간까지만 좁혀져서 그 구간을 시간마다 덮는다.
3. **본 실행을 05:30 KST 로.** 지금은 효과가 없다. 아래 "Hobby 제약" 참고.

### Hobby 제약 (2026-09-20 확인)

`vercel teams ls` → `maybeajs-projects` · Plan **hobby**.

| | 프로젝트당 크론 수 | 최소 간격 | 정밀도 |
|---|---|---|---|
| Hobby | 100개 | 하루 1회 | **시간 단위 (±59분)** |
| Pro | 100개 | 분 단위 | 분 단위 |

- **개수는 제약이 아니다.** 전 플랜 100개까지다. 따라잡기를 더 늘려도 된다.
- **분은 무시된다.** `30 20 * * *` 이라고 써도 Hobby 는 UTC 20:00~20:59 사이
  아무 때나 실행한다. KST 05:00~05:59 — 즉 30분 늦추기는 **지금 아무 효과가 없다**.
  Pro 로 올렸을 때 의도가 남도록 분 필드는 그대로 둔다.
- 따라잡기도 같은 이유로 06:00~06:59, 07:00~07:59 … 사이 어딘가에 돈다.

## 열린 결정 — 06:00 공개를 늦출 것인가

지금 구조는 여유가 1시간뿐이다(05시대 계산 → 06:00 공개). 네이버가 06시 이후에
올린다면 따라잡기로 메우더라도 **오전가가 06:00 에 안 나오는 날**이 생긴다.

며칠 재본 뒤 이렇게 판단한다.

- **도착이 매일 06:00 이전**이면 지금 구조를 유지한다. 오늘은 예외였다고 본다.
- **06:00 이후가 잦으면** 오전장 공개 시각 자체를 늦추는 것을 고려한다.
  Hobby 에서는 크론을 분 단위로 당길 수 없으므로 따라잡기 말고는 손쓸 방법이 없다.

**2026-09-21 관측 이후**: 06:00 을 유지하면 매일 아침 세 시간 남짓은 정가다.
그동안 화면은 정가에 전날 확정가 대비 등락률(+8% 안팎)을 붙여 "빵값이 올랐다"로
읽힌다. 값 자체는 사실이지만(몰도 정가를 받는다) 메시지가 나쁘다. 정가 구간에는
등락률을 감추거나, 정가 리셋(02:00)을 가격 산정 직전으로 옮겨 정가 구간 자체를
줄이는 쪽을 함께 검토한다 — 후자라면 전날 가격 이월이 다시 맞는 답이 된다.
  공개 시각은 제품 약속이라 코드가 아니라 기획에서 정한다. 늦출 경우
  잠금 가능 구간(06:00~15:59)과 예측 판정 시각("내일 06:00 오전가")이 함께 움직인다.

## 재는 법

가격 입력은 둘이고 도착 시각이 서로 다르다.

| 출처 | 무엇 | 쓰는 곳 | 언제 생기나 |
|---|---|---|---|
| 네이버 데이터랩 | D-2 검색지수 | 오전가·오후가 | 전날 것이 오전 8~9시대 (측정 중) |
| 한국은행 ECOS | 당일 시가 | 오후가만 | 외환시장 개장 09:00 이후 (측정 중) |

ECOS 종가는 15:30 확정인데 당일에는 올라오지 않는다 — 2026-09-21 16:17 에
당일 시가(1387)는 있고 당일 종가는 없었다. 오후가가 시가를 쓰는 이유다.

```bash
npm run probe:inputs                              # 한 번 재고 price-input-lag.tsv 에 붙인다
node scripts/price-input-probe.mjs --summary      # 출처·날짜별 "마지막 미도착 / 첫 도착"
```

새벽~오전만 촘촘히 걸면 도착 시각이 좁혀진다.

```
*/15 4-12 * * *  cd <repo> && node scripts/price-input-probe.mjs >> /dev/null
```

로그는 `price-input-lag.tsv`(gitignore). 열: 잰시각KST · 출처 · 필요한날짜 · 도착여부 · 실제마지막관측일 · 자정이후분 · 라벨.

## 측정 기록

| 잰 날짜 | D-1 | 마지막 미도착 | 첫 도착 |
|---|---|---|---|
| 2026-09-20 | 2026-09-19 | 05:21 (운영 크론) | 09:30 (수동) |
| 2026-09-21 | 2026-09-20 | 08:16 (운영 크론) | 09:09 (probe) |

이틀 관측이 겹치는 구간은 **08:16~09:09** 다. 05:30 본 실행은 아직 한 번도
성공한 적이 없다. 2026-09-21 에는 05:30·06·07·08시 네 회차가 모두 보류됐고,
오전장 내내(06:00~09:49) 화면이 정가였다.

따라잡기를 10시대까지 둔다. Hobby 는 그 시간대 안 아무 때나 돌아서 09시 회차가
09:00 정각에 걸리면 놓칠 수 있는데, 10시 회차가 있으면 늦어도 11:00 전에는
채워진다. 도착이 더 늦는 날이 나오면 11시대를 더한다.

## 공개된 확정가는 바꾸지 않는다 — 2026-09-20 은 예외로 바꿨다

원칙은 그대로다. **확정가는 한 번 공개하면 그 장이 끝날 때까지 고정이다.**
잠금과 예측이 전부 그 전제 위에 서 있고, 잘못 나간 날은 되돌리는 게 아니라
다음 장부터 바로잡는다.

2026-09-20 오전가는 예외로 다시 계산해 덮었다. 같은 판단을 다음에 되풀이하지
않도록 근거와 대가를 남긴다.

**바꾼 것** (KST 10시대, 오전장 진행 중)

| | 전 | 후 |
|---|---|---|
| 잉글리시 머핀 | 1,370 | 1,420 ▲ |
| 냉동생지 3종 | 19,870 | 20,130 ▲ |
| 글루텐프리 스콘 | 3,570 | 3,440 ▼ |
| 모닝롤 | 4,170 | 4,140 ▼ |
| 테트리스 브레드 | 10,220 | 10,130 ▼ |
| 글루텐프리 휘낭시에 | 3,320 | 3,320 — |

`signal_date` 가 2026-09-18 에서 2026-09-19 로 바뀌었고 몰에도 반영했다.
`daily_prices` 는 `(product_id, publish_date, price_session, formula_version)`
유니크라 행이 늘지 않고 제자리에서 덮인다.

진행 중이던 예측 2건(냉동생지 3종, 오른다 1 · 내린다 1)의 `reference_price_won`
도 19,870 → 20,130 으로 옮겼다. 판정은 저장된 기준가만 쓰므로 안 옮겨도 됐지만,
그러면 기준가와 그날 확정가가 갈라진 채 남는다.

**대가로 받아들인 것**

- 두 예측이 같은 기준가에 정반대로 걸려 있었다. 기준가를 옮기면 승패 경계선이
  함께 움직인다 — 09-21 오전가가 19,870~20,130 사이로 나오면 승자가 뒤집힌다.
  둘 다 운영자 본인 계정이라 받아들였다. **남의 예측이 걸려 있으면 하지 않는다.**

  이 우려는 **다음 날 실제로 실현됐다.** 09-21 오전가가 20,020원으로 나와
  19,870~20,130 구간 안에 들어왔다. 원래 기준가 19,870 이었다면 "오른다"가
  이겼을 것을, 옮긴 기준가 20,130 으로는 "내린다"가 이겼다. 승자가 그대로
  뒤집혔다. 가설이 아니라 사례다.
- 절반이 장중에 비싸졌다. 06:00 이후 그 가격을 보고 산 사람은 되돌릴 수 없다
  (Cafe24 주문 조회 권한이 토큰에 없어 확인도 못 했다).
- 잠금 1건(잉글리시 머핀 1,370원)이 몰 1,420원보다 낮아졌다. 일요일이라 오후가가
  없어 차액 쿠폰이 발급되지 않는다. 이것도 본인 잠금이라 보상 없이 두었다.
  16:00 부터 화면은 "차액 쿠폰 50원"이라고 말하지만 실제로는 없다.

**다음에는 안 해도 된다.** 이 날의 원인(이월값으로 가격 생성)은 막혔고, 같은
상황이면 이제 가격이 아예 안 나온다. 되돌릴 일 자체가 생기지 않는다.
