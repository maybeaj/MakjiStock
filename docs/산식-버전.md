# 산식 버전

운영 중인 산식·쿠폰 보상률은 DB `pricing_versions` 의 **가장 최근 행**입니다
(`supabase/migrations/010_pricing_versions.sql`, 읽기는 `lib/bread-market/policy-server.ts` `loadActivePolicy`).
한 행에 산식(`formula`)과 쿠폰 보상률 폭(`coupons`)이 함께 들어 있고, 버전 이름(`version`)이 그 묶음의 이름입니다.

버전 이름은 `daily_prices` 유니크 키에 들어가므로(`product_id, publish_date, price_session, formula_version`),
버전이 바뀌면 같은 날짜를 다시 계산해도 공개됐던 행을 덮어쓰지 않고 새 행이 생깁니다.
그래서 이름을 재사용하지 않습니다 — 공개된 확정가는 바꾸지 않는다는 원칙과 같은 이유입니다 (docs/네이버-검색지수-도착시각.md).

## 버전을 올리는 방법

어드민 `/admin/pricing` 에서 값을 고치고 저장합니다.

1. 초안을 고친다. 화면에서 고치는 값은 검색 가중치, 환율 배율(`fxWeight × fxScale`), 환율 할인·할증 상한, 환율 상승 반영 비율, 상품 할인 상한·하한, 쿠폰 보상률 폭 세 가지(안정형 오전·오후, 공격형)입니다. `fxScale`·반올림 단위 같은 나머지는 운영 버전 값을 그대로 이어받습니다.
2. 저장 전 검사(`checkPolicy`, 화면과 서버가 같은 함수)를 모두 통과해야 합니다. 상품 할인 상한 + 공격형 최대 ≤ 38%(`TOTAL_CAP_PCT`), 안정형 최대 < 공격형 최대, 할인 하한 ≥ 0(정가 초과 금지), 쿠폰 폭은 1% 이상 정수, 산식 값은 허용 범위 안.
3. 90일 백테스트로 운영값과 초안을 비교합니다 (`lib/admin/backtest.ts`). `daily_prices` 에 저장된 검색지수·환율 입력을 그대로 두고 `calculateDay` 로 다시 계산하며, 상품별 마진 상한도 반영합니다(지금은 6종 모두 마진 값이 비어 정책 상한을 씁니다).
4. 저장하면 다음 버전 이름(`nextVersion`, v1.4 → v1.5)으로 새 행이 **추가**됩니다. 기존 행은 고치거나 지울 수 없습니다(update·delete·truncate 트리거가 막음). 화면을 연 뒤 다른 사람이 먼저 저장했으면(`baseVersion` 불일치) 저장을 거절합니다. 바뀐 값은 변경 기록(`admin_audit_log`, `/admin/audit`)에 자동으로 남습니다.

저장한 순간부터 운영값입니다. 다음 가격 크론과 쿠폰 발급(공격형·안정형·판정 쿠폰), 사용자 화면이 모두 새 행을 읽습니다.
가격 크론(`daily-pricing`)은 DB 를 못 읽거나 행이 검사를 통과하지 못하면 코드 대비값으로 계산하지 않고 503 으로 보류합니다. 안정형 바로 받기(`predictions/instant`)도 같은 경우 503 이고, 화면이 본 버전과 운영 버전이 다르면 409 로 거절합니다.

`config/pricing-products.json` 의 `pricing`·`formulaVersion` 과 `lib/bread-market/policy.ts` 의 `DEFAULT_POLICY` 는 이제 **대비값**입니다. DB 를 못 읽을 때 화면이 쓰는 값이고, 백테스트 스크립트(`scripts/simulate-pricing.mjs` 등)가 읽는 값입니다. 둘과 010 시드 행이 v1.4 로 같은지 `tests/policy.test.mjs` 가 지킵니다. 어드민에서 v1.5 이상을 저장해도 이 파일들은 따라 바뀌지 않습니다.

2026-10-07 운영 DB 에는 v1.4 한 행만 있습니다(어드민 저장 이력 없음). 아래 v1.0~v1.4 기록은 어드민 이전에 코드로 바꾼 버전입니다. v1.4 는 010 마이그레이션이 첫 행으로 넣었습니다(`actor` = '기록 이관'). v1.5 부터는 `pricing_versions` 의 `note` 와 `/admin/audit` 이 기록입니다.

## v1.4 — 2026-09-28

**환율 상승도 하락과 같은 크기로 전부 반영합니다.** 검색 가중치, 상품 할인 상한 25%, 정가에서 멈추는 하한 0, 쿠폰은 v1.3 그대로입니다.

| | v1.3 | v1.4 |
|---|---|---|
| 환율 상승 반영 비율 (`fxRisePassThroughPct`) | 50% (× 7) | **100% (× 14)** |
| 환율 상승 쪽 상한 (`fxSurchargeCapPct`) | −14%p | **−28%p** (하락 쪽 +28%p 와 같게) |

90일 924세션 기준 변화:

- 상품 할인 평균 **12.55% → 11.86%**
- 정가 그대로인 세션 0% → **2.6%** (환율이 오른 날 할인이 0 까지 줄어든 경우. 하한 0 이라 정가를 넘지는 않는다)
- 같은 날 오전↔오후 가격 차이 평균 6.28% → **7.69%**, 오전가 = 오후가 0.3% → 0%
- 25% 상한 도달은 3.4% 로 그대로

하한 0 을 풀어 할증을 허용하면 같은 90일에 정가 초과 2.6%, 최대 정가 +5.9% 였습니다. 지금은 허용하지 않습니다.

이미 공개된 v1.3 행은 그대로 둡니다.

## v1.3 — 2026-09-27

**상품 할인 상한을 28% → 25%로 낮추고, 쿠폰 금액에 정가의 13% 천장을 걸었습니다.** 가중치와 환율 구간, 쿠폰 보상률 폭은 v1.2 그대로입니다.

| | v1.2 | v1.3 |
|---|---|---|
| 상품 할인 상한 (`discountCapPct`) | 28% | **25%** |
| 판매가 하한 | 정가의 72% | **정가의 75%** |
| 쿠폰 금액 | 판매가 × min(R, 38 − 발급 시점 할인율) | **min(판매가 × R, 정가의 13%)** |

바꾼 이유는 둘입니다.

1. **v1.2는 38%를 보장하지 못했습니다.** 쿠폰은 발급 시점 할인율로만 잘랐는데, 공격형(24시간)·안정형(3시간)은 받은 뒤 오후가가 더 내려간 장에서도 쓰입니다. 오전 할인 0%에 공격형 13%를 받고 오후 할인 28%에 쓰면 40.9%입니다. 90일 백테스트에서는 한 번도 없었지만(최대 36.6%) 막는 장치가 없었습니다.
2. **28%를 두고 38%를 지키려면 공격형을 정가의 10%에서 잘라야 합니다.** 그러면 공격형 최대치가 안정형 최대 10%와 같아져, 모른 채 거는 공격형을 고를 이유가 사라집니다. 25% + 13% = 38%로 맞추면 공격형 13%를 그대로 살립니다.

90일 924세션 기준 비용: 원시 할인이 25%를 넘은 세션 31개(3.4%)가 최대 3%p 덜 할인되고, 상품 할인 평균은 **13.00% → 12.93%** 입니다. 38% 초과는 이론상으로도 0이 되고(최대 38.0%), 공격형 최대 지급은 정가의 10.0% → **12.9%**, 안정형은 9.9%로 그대로입니다.

이미 공개된 v1.2 행은 그대로 둡니다.

## v1.2 — 2026-09-23

**상품 할인 상한을 38% → 28%로 낮췄습니다.** 가중치와 환율 구간은 v1.1 그대로입니다.

| | v1.1 | v1.2 |
|---|---|---|
| 상품 할인 상한 (`discountCapPct`) | 38% | **28%** |
| 판매가 하한 | 정가의 62% | **정가의 72%** |
| 쿠폰과 합친 주문당 상한 (`TOTAL_CAP_PCT`) | 38% | 38% (그대로) |

쿠폰 폭도 같은 날 바꿨습니다. 쿠폰은 산식 버전과 따로 관리하지만(`lib/bread-market/reward-policy.ts`) 두 값이 한 덧셈으로 묶여 있어 함께 적습니다.

| 쿠폰 | 전 | 후 |
|---|---|---|
| 안정형 · 오전장 | 13~15% | **7~10%** |
| 안정형 · 오후장 | 10~12% | **5~7%** |
| 공격형(예측) | 5~20% | **5~13%** |

28% + 오전 안정형 최대 10% = 38%. 안정형은 합계 상한에 잘리지 않고, 공격형 11~13%만
상품 할인이 25%를 넘는 날에 잘립니다.

이미 공개된 v1.1 행은 그대로 둡니다. 이미 제출한 공격형 예측은 저장된 보상률을 씁니다.

## v1.1 — 2026-09-22

**오전장 환율 구간을 전영업일 안으로 좁혔습니다.**

| | v1.0 | v1.1 |
|---|---|---|
| 오전 06:00 | 전전영업일 종가 → 전영업일 종가 | **전영업일 시가 → 전영업일 종가** |
| 오후 16:00 | 전영업일 종가 → 당일 시가 | 그대로 |

v1.0 은 오전장 구간이 전날 오후장과 겹쳤습니다. 같은 환율 움직임이 이틀에 걸쳐
두 번 가격에 반영됐고, 특히 화요일 오전은 주말 사흘치 갭을 통째로 받았는데 그
갭은 이미 월요일 오후장이 받은 것이었습니다.

v1.1 에서는 두 장이 시간을 이어 덮습니다.

```
전영업일 시가 ──[오전장]──> 전영업일 종가 ──[오후장]──> 당일 시가
```

90일 924세션 기준 변화:

- 38% 상한 도달 **11회 → 0회** (주말 갭 중복이 만들던 극단값이 사라짐)
- 오전 환율 변동 |평균| 0.406% · 오후 0.279% — 하루 안의 시가-종가가 오버나이트 갭보다 넓다
- 오전 할인율 평균 13.73% · 오후 11.08%
- 같은 날 오전↔오후 가격 차이 평균 7.5% → 6.5%

전영업일 시가가 없으면 오전 세션을 만들지 않습니다. 주말은 전과 같습니다 —
전영업일 시가는 있고 당일 시가만 없어 오전가는 나오고 오후가는 오전가를 유지합니다.
